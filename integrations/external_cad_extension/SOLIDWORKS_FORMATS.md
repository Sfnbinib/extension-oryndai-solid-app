# SolidWorks Extension Formats For ORYND CAD Bridge

This project must keep three target formats separate.

## 1. Macro Pack - Fastest Test Target

Purpose:

```text
Generate macro -> user reviews code -> user runs macro in SolidWorks -> model appears
```

Typical files:

- `.swp` - SolidWorks VBA macro project file, commonly used by end users.
- `.swb` - SolidWorks macro file format used in some workflows.
- `.bas` - exported/importable VBA module text.

Current prototype status:

- We generate `.bas` text files.
- `.bas` is good for review, static validation, source control, and import into a macro project.
- We do not yet generate a binary `.swp`.
- We have not runtime-tested the macro in SolidWorks.

Recommended next step:

```text
Keep `.bas` as source-of-truth -> import into SolidWorks macro editor -> save as `.swp` on a Windows/SolidWorks machine.
```

## 2. SolidWorks Add-in - Real Extension Target

Purpose:

```text
Install once -> appears in SolidWorks Add-Ins -> has toolbar/task pane/menu -> calls ORYND CAD Bridge tools
```

Typical implementation:

- COM-visible `.dll`, usually C#/.NET Framework or C++.
- Implements SolidWorks add-in lifecycle, including connect/disconnect.
- Registered in Windows registry under SolidWorks Add-Ins keys with a GUID.
- Installer registers COM and adds load/startup metadata.
- UI can be command manager buttons, menus, task pane, or property manager pages.

What this add-in should do for ORYND:

- Show prompt/input UI or open the local companion UI.
- Send prompt/image/context to the local ORYND CAD Bridge process.
- Show operation plan and macro/code preview.
- Require approval before execution.
- Execute only validated operations/macros.
- Save/export STEP/STL/OBJ.

Current prototype status:

- Scaffolded under `solidworks_addin/`.
- Includes C#/.NET Framework project, COM identity, right-side Task Pane control scaffold, local bridge client, and registration script template.
- Not compiled or runtime-tested in SolidWorks yet.
- No toolbar icons, signed installer, or verified registry packaging yet.

Recommended add-in architecture:

```text
SolidWorks Add-in DLL
  -> local HTTP/MCP bridge
  -> ORYND CAD Bridge planner/validator/macro engine
  -> SolidWorks API execution
```

Reason:

```text
Keep AI/model/search/security logic outside the SolidWorks process first.
The add-in becomes a thin trusted host/runner.
```

## 3. Local Companion App / MCP Server - Model Orchestration Target

Purpose:

```text
External model or local UI controls CAD Bridge without being inside SolidWorks.
```

Current prototype status:

- Local CLI exists.
- Local companion web UI/dev preview exists.
- Local stdio MCP server exists.
- This can already generate plans/macros/validation reports.

How it connects later:

```text
Claude/Codex/Cursor/ChatGPT via MCP
  -> ORYND CAD Bridge tools
  -> macro/operation plan
  -> SolidWorks macro pack or add-in runner
```

## Packaging Strategy

Recommended order:

1. Macro pack source:
   - `.bas` generated by this project;
   - saved artifacts;
   - manual import into SolidWorks;
   - runtime hardening on Windows/SolidWorks.

2. SolidWorks add-in UI:
   - CommandManager toolbar;
   - task pane or WebView2 task pane;
   - PropertyManagerPage for structured parameters;
   - local companion process behind the scenes.

3. Companion/MCP process:
   - local service;
   - settings/account/trial/API key;
   - MCP server;
   - validated macro generation.

4. SolidWorks add-in packaging:
   - C# COM-visible DLL;
   - toolbar/task pane;
   - local bridge connection;
   - explicit execution approval;
   - installer/registry packaging.

## Current Gap

The current generated `.bas` is not enough to claim:

```text
Installed SolidWorks extension
```

It is accurate to claim:

```text
Offline macro source generator + validator + MCP/local companion prototype
```
